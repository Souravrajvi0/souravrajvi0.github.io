#4 SSH sandbox bypass via Python librariesunslothai/unsloth#10642
AI agentssandbox securitySSHparamikoPythonUnsloth Studiobackend engineeringopen source

The agent sandbox blocked the ssh command. It did not block ssh.

I found this while working on the AI agent tool-calling sandbox in Unsloth Studio's backend.

The rule was simple:
ssh, scp and sftp were hard-blocked at execution time.
Even after the user approved the tool call.

So the policy looked airtight.

Then I looked at the Python side.
paramiko, asyncssh and fabric could open the same connection.
Especially when the hostname was a variable that static analysis couldn't resolve.

Same capability. Two paths. Only one of them had a guard.

Easy fix. Block the libraries too.
Except it wasn't.

That would make the sandbox consistent, but also useless for the one legitimate workflow people actually want: an agent deploying to a server the user has reviewed and approved.

A blanket ban only pushes people toward bypasses.

So I replaced the hard blocklist with a per-session approved-server allowlist, and put both paths behind the same policy:
→ Terminal: ssh, scp, sftp
→ Python: paramiko, asyncssh, fabric connect patterns
→ Dynamic hosts (ssh $HOST, connect(hostname)) fail closed until a literal host is approved
→ Allowing a tool call records that target host for the session only

The model proposes a command. The user sees it and approves it. The host is recorded. Later calls to that host work. Everything else stays blocked.

I also exposed small API endpoints to approve and list hosts per session, and added a large regression suite covering host extraction from shell commands and Python AST, gating, and execution.

What I learned:

1. A security policy has to cover the capability, not the tool name.
If you block a CLI but not the library that does the same thing, you've blocked a spelling.

2. Dynamic values are where guards quietly fail.
If you can't resolve a host statically, the safe answer is "not approved yet", not "probably fine".

3. Hard blocks and approvals are different tools.
A hard block says never. An allowlist says only what a human has seen. Agents need the second one.

4. Scope approvals narrowly.
Per session, per host. Not forever, not for everything.

5. Put every path behind one policy.
Two code paths with two implementations of the same rule will drift.

Agent safety isn't about saying no louder. It's about making "yes" specific.

#5 Token-shaped string took the operator cache fast pathunslothai/unsloth#10264
API securityHugging Face HubauthorizationcachingPythonUnsloth Studiobackend engineeringopen source

I sent a fake API key. Unsloth Studio served me cached data anyway.

Working on Hugging Face Hub token authorization in the Unsloth Studio backend, I ran into this.

The earlier fix keyed every disk-cache gate on one check: is_anonymous(hf_token).

That is only true when the caller sent no token. So the gate was really asking "Did the caller send nothing?" and not "Is this credential allowed to see this repo?"

Any token-shaped string left the anonymous sentinel and took the same fast paths as the operator:
→ cached dataset previews
→ the chat template walk
→ config and audio probes
→ GGUF listings

A dummy string was enough.

There were many gates across routes, services and utils. Eight separate checks would drift apart, and the next endpoint would forget one. So I wrote one helper and applied it at all of them.

It treats the three caller states differently:
→ the sentinel: no cache
→ ambient or UI session: cache, with no extra Hub call
→ explicit token: cache only after HfApi.repo_info succeeds for that specific repo

The answer is memoized for 60 seconds, so the Hub round trip isn't paid on every request.

Details that mattered:
→ Unexpected types fail closed instead of falling into the ambient branch
→ Local paths are never probed, so a caller's path and bearer token don't go over the wire
→ Offline, an explicit token is denied rather than stalling on a probe

UI sessions keep the fast path. A made-up API key doesn't.

I added regression tests for the caller-identity cases: 84 passed. Two others need the datasets package and were skipped, same as before.

Four lessons:

1. A sentinel identifies a class of caller, not a credential.
"Not anonymous" is not the same as "authorized".

2. Gate on the resource, not the string.

3. Centralize the check. One helper at many gates beats many slightly different checks.

4. Default to deny.
Anything unexpected should land on the closed side.

A cache is an authorization boundary too.

#6 Batch retrieve leaked provider file idsBerriAI/litellm#34092
LiteLLMLLM gatewayAPI securityauthorizationbatch APIOpenAIPythonbackend engineeringopen source

Every route in the LiteLLM batch flow worked. Then the results download returned a 500.

And that wasn't the worst part.

I traced it while working on the LiteLLM proxy, the LLM API gateway.

The flow:
→ upload a JSONL, get a managed file id back
→ create a batch
→ poll until it completes

Then the completed batch response handed back a raw provider output_file_id. An OpenAI-style file-abc123, not the managed id the gateway had given out everywhere else.

Downloading it through the gateway failed, because no managed-file row existed for it. Worse, raw ids skip managed-file ownership checks.

On the old code, a different key on the proxy could download another user's batch output. I reproduced that against a live proxy with a real batch: the intruder got a 200.

A unified-id lookup on retrieve only works if the row already exists, and terminal batches persisted before output registration existed had none. So retrieve now registers the missing row itself.

Then the real question: who owns it? The caller who happened to retrieve it would hand the file to whoever polled first. Instead the row goes to the durable batch owner from the stored batch record. If there is no real owner on the record, registration is skipped rather than guessed.

Output and error ids now always come back as unified managed ids.

After the fix, on the same batch and database state:
→ owner retrieve returns a unified id
→ owner download returns 200
→ intruder download returns 403

I added regression tests, including a cross-user denial test that runs the real managed-files hook.

What I took from it:

1. A convenience field can be an authorization bypass.
A raw upstream id skips every check keyed on your own id.

2. Ownership belongs to the creator.
Not whoever touched the resource last.

3. Heal missing state at the read path.
Legacy rows exist in production.

4. Prove it with two identities.
A single-user test can pass while another user can still read the data.

Still open: concurrent retrieves can mint separate ids for the same file. Both carry the same owner, so authorization holds.

An id the gateway didn't issue is an id the gateway can't protect.

#7 Desktop SPA on loopback without opening the doorunslothai/unsloth#10847
Unsloth Studiodesktop appDNS rebindingloopbackPythonFastAPIAPI securitybackend engineeringopen source

http://127.0.0.1:8888 returned 404. The same app on the LAN IP worked.

I ran into this in the backend of the Unsloth Studio desktop app.

Desktop runs the backend with --api-only on 127.0.0.1. The packaged web UI was only served to the Cloudflare edge or the LAN listener.

So the one address you'd naturally try first, localhost, got nothing.

There was a second cost. Loopback is a browser secure context, so mic dictation through getUserMedia was blocked there too.

Quick fix. Serve the UI on loopback.
The obvious fix had a catch.

"Looks like loopback" is exactly the kind of check that gets bypassed:
→ a reverse proxy on the same machine makes remote traffic look local
→ a forwarded header can claim anything
→ a malicious page can rebind a hostname to 127.0.0.1

So the gate admits a request only if all of these hold:
→ the listening socket is loopback
→ the peer address is loopback
→ the Host header is loopback
→ no Forwarded, X-Forwarded-*, X-Real-IP or CF-Connecting-IP header is present

I reused the same check that already gates bootstrap password injection, rather than inventing a second definition of "local". Bootstrap injection itself is unchanged.

I ran a real uvicorn server and compared base against the fix:
GET / via 127.0.0.1: 404 -> 200
GET / with Host: localhost: 404 -> 200
GET /chat deep link: 404 -> 200
GET / with X-Forwarded-For: 404 -> 404
GET / with CF-Connecting-IP: 404 -> 404
GET / with Host: evil.example: 404 -> 404

The targeted test files ran 246 passed. Three updated tests fail on main.

What I learned:

1. Loopback is a combination of facts, not one.
Socket, peer and Host all have to agree.

2. Proxy headers are evidence of a proxy.
If they're present, it isn't a direct local browser.

3. The Host header is attacker-influenced.
Checking it is what stops DNS rebinding.

4. Reuse the existing trust predicate.
Two definitions of "local" will eventually disagree.

5. Test the rejections as carefully as the success.
The 404s that stayed 404 were half the point.

Making something reachable is easy. Making it reachable only to the right caller is the work.

#8 Tool file worked in test-run, failed when publishedlanggenius/dify#41300
DifyLLM workflowsAI agentsfile accessauthorizationPythonbackend engineeringopen source

The workflow worked in the test-run. The published version sent the LLM no image.

Tracing an LLM workflow in Dify's backend, I hit this: a workflow that downloads an image in a tool node and passes it to a later LLM vision node.

In the orchestration test-run: fine.
Invoked from an Agent as a published workflow: the prompt arrived with files: [].

No error. Just a missing image.

The difference was the file-access scope.
→ Orchestration binds an Account scope, so plugin ToolFile rows are readable
→ Agent chat binds an EndUser scope

And plugin uploads often store ToolFile.user_id as a different identity than the chatting end user. The later lookup then fails the ownership filter and the file silently drops out.

The obvious fix. Loosen the ownership check for tool files.
It wasn't that simple.

That ownership filter is there for a reason. Relaxing it would let one user's file be read by another, and I'd have traded a missing image for a data-access problem.

So I followed a pattern Dify already has for upload files: an explicit grant.

When the tool message transformer produces a tool_file_id, it records that id on the current FileAccessScope. Later nodes in the same execution can attach those files.

The grant is:
→ per execution, not global
→ limited to files this run produced
→ additive: ungranted tool files still require a matching user_id

I added tests for both sides: the transformer grants the file to the current end-user scope, and build_from_mapping accepts a granted tool file for a different end user. I also ran the existing file-access unit tests.

What I learned:

1. Silent failures are the expensive ones.
An empty file list looks like success until someone reads the output.

2. Test-run and production can run under different identities.
If a workflow passes in one scope, check it in the other.

3. Don't loosen a check to fix a symptom.
Ask what the code legitimately needs access to, and grant exactly that.

4. Grant by provenance.
A file produced by this run is a different thing from a file that merely exists.

5. Reuse the established pattern.
Mirroring the upload-file grant kept the change small and easy to review.

The safest fix to an access bug is a narrower grant, not a weaker check.

#9 Zotero RAG connector hardeninginfiniflow/ragflow#19742
RAGRAGFlowSSRFAPI securityPythonGodata connectorsopen source

Adding a new RAG data source looks like an integration task.
With Zotero, it turned out to be a security task.

I added Zotero as a data source in the RAGFlow RAG pipeline, with connectors in both Python and Go.
The happy path is simple:
Pull the PDFs from a user's library.
Parse them.
Index them for retrieval.

Easy feature. The details mattered.

The connector takes a user-supplied WebDAV URL and an API key, and then makes outbound requests from the server.
That is a textbook SSRF surface, plus a credential that must never end up at the wrong host.

The naive version:
Fetch whatever URL the user typed.
Send the API key with every request.
Follow redirects.

Here is what I did instead:
→ WebDAV is HTTPS-only, validated locally before any network call
→ An SSRF check on the resolved address, with DNS pinned so the host can't change between the check and the request
→ The Zotero API key is sent only to api.zotero.org, and redirects are followed manually without forwarding the key
→ A cap on file redirects, and oversized attachments are skipped
→ No default WebDAV URL, so we never claim Zotero hosts WebDAV somewhere it doesn't

The other problem was scale.
A research library can be big, and buffering all of it in memory before indexing is a production reliability problem waiting to happen.
So sync is incremental and batched: PDFs are yielded in the Python connector and downloaded per batch via NextBatch in the Go one.

What I learned:

1. A data connector is an outbound-request feature.
Anything that fetches a user-controlled URL needs SSRF protection from day one.

2. Checking a hostname is not enough.
If you resolve it twice, the answer can change. Validate the IP and pin it.

3. Credentials should be scoped to a host, not to a request.
Redirects are where API keys quietly leak.

4. Validate configuration before touching the network.
Fail fast on bad settings with a clear error.

5. Stream your sync.
Batching keeps memory flat no matter how large the source is.

Good AI engineering isn't only about retrieval quality. Backend engineering means making sure the pipeline feeding your RAG system can't be turned against you.

An integration isn't done when it syncs. It's done when it fails safely.

#10 Chat-template markup injectionunslothai/unsloth#7334
LLMprompt injectionchat templatesUnslothAI securityPythonagentsopen source

A string in a tool result could forge an assistant turn.
No exploit. Just text.

The report that started this, in Unsloth's LLM chat-template handling, was small:
A literal </think> in a user message was read as the end of the reasoning block.
The rest of the model's thought leaked into the visible answer.

Then I looked closer.
The same hole meant a tool result containing
<|start|>assistant<|channel|>final<|message|>
could open a whole assistant turn that the model never wrote.

Both were the same bug:
Text the client controls reaches a chat template as markup instead of as content.

The fix looked simple. It wasn't.

The naive fix is to strip </think>.
But the problem isn't one token. Every model family has its own control syntax:
→ ChatML and Harmony style pipe tokens
→ DeepSeek's fullwidth-bar tokens
→ Mistral and Llama-2 [INST] brackets
→ Qwen tool XML, including the tools catalog block
→ Gemma turn delimiters

So the fix in Unsloth Studio neutralizes control markup with one small substitution, a space after the opener, so the text stays readable but is no longer a delimiter.

The harder question was where to apply it.
Not just the message content. Also:
→ tool result names
→ replayed tool call arguments
→ tool catalogs copied from remote MCP servers
→ the render paths that bypass the shared template function, including llama-server passthrough and token counting

There were also trade-offs I wrote down instead of hiding.
The marker list is closed on purpose, so ordinary text like <div> or [TODO] is untouched.
Replayed assistant content only gets its turn boundaries broken, because rewriting its own think and tool markup would corrupt the transcript.
And a tool whose name contains control markup is dropped with a warning, since rewriting a dispatch name would silently break the call.

For verification, I rendered 12 real upstream templates. A hostile paste forged structure in every one before the fix and in none after, while benign prompts rendered byte-identically.

What I learned:

1. Prompt injection isn't only semantic.
It can be structural. The template is a parser, and the parser trusts its input.

2. Sanitize at every point where text reaches the template.
One missed render path is the whole vulnerability.

3. Don't rewrite identities.
Fields used for dispatch can't take the same treatment as content.

4. Test against the real templates, not a model of them.

5. Write the trade-offs down.
A closed list with known costs beats a clever regex nobody can reason about.

If your template can't tell content from control, your user can.

I forced the model to call web_search. It answered from memory instead.

The request to Unsloth's LLM tool-calling path was explicit:
tools enabled, web_search selected, tool_choice forced.
On a local GGUF model, no tool ran.
Leave the selection out and web_search worked fine.

My first suspicion was the hosted-tool logic that decides which tools stay local.
It was the wrong place.
A loaded GGUF has no provider type, and the local catalog already kept web_search.

The real cause was one line.
The agentic loop hardcoded tool_choice to "auto".
So the forced choice never reached llama-server. The client asked for one thing, and the backend quietly sent another.

I expected a quick patch. The details mattered.

Just forwarding the value would introduce a new bug.
If you force a tool on every turn, the model can never stop calling it and answer in prose.

So the design is:
→ Forward tool_choice through both the OpenAI chat and Anthropic routes
→ Honour a forced function on the first turn
→ After a tool actually runs, drop back to "auto" so the model can answer
→ Validate that the forced tool is actually enabled
→ Honour "none" as a real value

Hosted providers keep their behavior: web_search without run_tools_locally stays hosted.

I added tests for the forced-then-auto sequence at the llama-server payload level, for the issue-shaped request entering the GGUF loop with the forced choice, and for the hosted-versus-local discriminator.

What I learned:

1. A hardcoded default is a silent override.
If a user-facing parameter exists, trace it all the way to the wire.

2. Don't trust the first suspect.
I looked in the routing logic. The bug was in the loop.

3. Forcing is per-turn, not per-request.
A forced tool call is an opening move, not a standing order.

4. Test the outgoing payload.
The assertion that matters is what llama-server actually received.

5. Keep API parity.
OpenAI-style and Anthropic-style routes should behave the same for the same intent.

An option that's accepted but never forwarded is worse than one that's rejected.

#13 max_completion_tokens retry for custom gatewaysunslothai/unsloth#10837
LLMOpenAI-compatible APIAzure OpenAIAPI compatibilitystreamingPythonUnslothopen source

Every request failed with the same error:
Unsupported parameter: 'max_tokens' is not supported with this model. Use 'max_completion_tokens' instead.

The setup: Unsloth Studio pointed at a custom OpenAI-compatible LLM API gateway in front of Azure-hosted gpt-5.x and o-series models.
Unsloth Studio sent max_tokens.
The gateway wanted max_completion_tokens.

The reason was simple.
Only the real openai provider type sent max_completion_tokens.
Everything else got max_tokens.

The obvious patch had a catch.

The naive fix: send max_completion_tokens for custom providers too.
That breaks the other side.
vLLM, llama.cpp and many other servers only know max_tokens.
"OpenAI-compatible" is a spectrum, and I can't tell where a gateway sits on it from its URL.

So I made the client learn from the server instead:
→ The first request is unchanged, so servers that only know max_tokens see no difference
→ If the upstream answers 400 and the error actually names max_tokens, resend once with max_completion_tokens
→ Match on the structured error first (param and code), with a substring fallback for non-JSON bodies
→ Any other 400 surfaces exactly as before, and a failing retry does too

Streaming was the tricky part.
The retry has to happen before any bytes reach the client.
The status check runs before anything is yielded, so the retry is invisible, and the stream body itself is untouched.

For tests, I drove the real client against a loopback HTTP server: stream and non-stream retry on the wire, an unrelated 400 is not retried, plus the error-matching cases. The two wire tests fail with the call sites reverted.

What I learned:

1. Compatibility is negotiated, not assumed.
When you can't know the dialect up front, let the server tell you.

2. Keep the common path byte-identical.
Retry logic should only exist on the failure path.

3. Retry narrowly.
One retry, only on a specific error, only for a specific parameter.

4. Streaming changes where you can recover.
Retry before the first yield, or you can't hide it.

5. Test over real HTTP.
Mocking the client would never have proven the wire behavior.

The best compatibility layer is one the user never notices.

#14 Wiki pages never retrievedinfiniflow/ragflow#18787
RAGRAGFlowknowledge compilationretrievalPythonopen sourceAI engineering

The wiki pages were in the index. They showed up in the UI. They never came back as RAG context.

The gap was in the RAG pipeline of RAGFlow, in its Knowledge Compilation feature.

Compiled wiki pages were browsable in Artifacts.
But when I queried the knowledge base, retrieval acted like they didn't exist.

Nothing crashed.
No error.
Just silent misses.

The graph rows from the same pipeline (wiki_entity, wiki_relation) were retrievable.
The pages weren't.

That difference was the clue.

The retriever always filters on available_int=1.
The incremental wiki persist path wrote pages and canonical entities without available_int, without doc_id, and without content_with_weight.

So the data was there, but every retrieval gate excluded it.

Quick fix. Just stamp the fields.
It wasn't that simple.

There was a second gate: _prune_deleted_chunks.
It drops hits whose parent document no longer exists.
Wiki pages use the KB id as a sentinel doc_id, or have none at all, so once source-document chunks were in the same result set, the pages got pruned as "orphans".

And the naive fix there is also wrong.
"Keep everything with a missing doc_id" would let stale chunks from deleted documents back in.

So the final design:
→ persist stamps available_int=1, doc_id=kb_id and content_with_weight on pages and canonical entities
→ FINALIZE backfills those fields on re-run, so existing pages become retrievable without a full rewrite
→ pruning keeps KB-scoped rows (doc_id equals the KB id, or an explicit compilation marker)
→ rows from a deleted source document are still dropped

I added regression tests for pages mixed with live and deleted source chunks, pages that omit doc_id, and the FINALIZE backfill.

What I learned:

1. "Visible" and "retrievable" are different properties.
If the UI reads one path and the retriever reads another, a feature can look finished while doing nothing for the LLM.

2. Retrieval filters are part of your schema contract.
Every field a filter touches has to be written by every producer, not just the first one you built.

3. Compare the rows that work with the rows that don't.
Graph rows stamped the fields. Pages didn't. That diff pointed straight at the cause.

4. Cleanup logic needs an explicit scope.
"Missing parent means stale" is only true if you define which rows have a parent in the first place.

5. Ship the backfill with the fix.
Fixing future writes does nothing for data that's already in the index.

A RAG system doesn't fail when retrieval returns the wrong thing. Sometimes it fails by quietly never returning the right one.

#15 Credential guard hangs the terminal toolunslothai/unsloth#12087
LLM agentstool callingsecurityPythonUnsloth Studioproduction reliabilityopen source

The terminal tool call never returned. It just stayed on "Running" past the max duration.

This was in Unsloth Studio's LLM agent tool calling, and the cause wasn't the shell command.
It was the safety check in front of it.

The setup: before an LLM-issued command runs, a guard scans it for references to Studio's credential files.
To catch tricks like d=../..; cat "$d/auth.db", the guard expands shell assignments first.

Then someone runs something harmless:

echo "A=$A B=$B"

The assignment A=$A B=$B refers to itself.
The expansion fed its output back into itself.
It recursed without bound.

And it ran synchronously on the backend event loop, holding the GIL.
So no tool result was logged, no completion reached the UI, and the whole server was stuck behind a log message.

Easy fix. Add a recursion limit.
Except it wasn't.

A flat limit alone creates a different problem:
→ too low, and legitimate long alias chains get refused
→ too high, and you still burn CPU on the event loop
→ and if hitting the limit means "allow", you've built a bypass

So the fix has three parts:
→ resolve a self-reference against the earlier binding (or empty) instead of expanding it into itself
→ bound the depth and the growth of the expanded text, while still allowing long finite chains
→ when the budget runs out, fail closed and refuse the command

I also made the guard scan assignment-like text inside quotes separately, so a log message shaped like an assignment can't overwrite a real binding, while real quoted shell programs are still inspected.

Regression tests cover quoted self-references, long credential and harmless alias chains, scan exhaustion, and growing unresolved assignments.

What I learned:

1. Security checks are code on your hot path.
A guard that can hang is an availability bug, and in an agent loop that means every tool call stalls.

2. Interpreters need budgets.
Any time you expand, resolve or evaluate user-influenced input, put a hard bound on depth and size.

3. Fail closed when the budget is exhausted.
If the guard can't finish its analysis, it can't claim the command is safe.

4. Don't let blocking work sit on the event loop.
One synchronous scan can freeze every other request.

5. Self-reference is a normal input.
A=$A isn't clever, it's just shell. Treat it as a case to resolve, not a case to hope doesn't happen.

A safety check that can hang is not a safety check. It's an outage with extra steps.
